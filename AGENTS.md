# Standing user requirements for Bingo reviews and fixes

The user explicitly requires fixes to remain fixed. Apply these requirements in every future review and fix pass on this project.

1. **No regression is an acceptance requirement.** Preserve `SimplifiedGameRules.md`, existing intentional behavior and working features. A patch that reintroduces a previously fixed issue is incomplete and must not be accepted.
2. **Prove the specific defect before and after the fix.** Add a regression test reproducing the reported scenario; record its failure against the affected version and its passing result after the fix. If pre-fix reproduction cannot be executed, state that limitation and do not describe it as executed proof.
3. **Test the actual production path.** Tests must exercise the implementation used by gameplay, packet handling and recovery. A separate test-only simulation or copied version of the intended logic cannot establish that a production callback bug is fixed. Expose a small shared production test seam when needed, preserving behavior.
4. **Keep previous regression coverage.** After each relevant change, run the previous issue regressions, the affected event-order/countdown/lifecycle cases and the normal suite. Cover the running handler and cold recovery when both paths implement the behavior. Do not weaken assertions or remove a valid regression merely to obtain passing results.
5. **Track every issue to its proof.** Maintain issue ID, affected production path, permanent regression-test name, before/after evidence and current verification status in the change log. A changed code branch or higher passing-test count alone is insufficient to close an issue.
6. **Make every later review check for recurrence.** Recheck previous findings alongside new changes. Label an old defect returning as a regression. Distinguish confirmed code defects, executed reproductions and missing verification; do not present a test-coverage gap as a reproduced gameplay failure.
7. **Do not declare completion with unresolved regressions or verification gaps.** Report any failure or missing production-path evidence explicitly. Preserve the existing review authorization limits; these standing requirements do not authorize additional rounds, deployments or gameplay-policy changes.
