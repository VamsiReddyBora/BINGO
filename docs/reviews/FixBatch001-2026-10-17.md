## Implemented fixes

### G1 — P1: stale host snapshots deleting accepted selections

Production reconciliation now validates the match, original host, snapshot sequence, accepted turn and committed history before calculating any board replacement. A stale/replayed snapshot returns without changing boards, history, pause UI, turn, outcome or reconciliation status.

`MultiplayerSnapshotReconciler.kt` separates accepted host picks from unconfirmed local picks. An open-turn sample retains a pick still in flight; once the host closes that turn without accepting it, the pending mark can be removed. The resulting boards and parallel histories are prepared together. Existing board layouts and win detection use `BingoEngine`.

Host snapshots receive increasing sequences at the shared broadcast entry point. That fence is saved before MQTT publication. Guest acceptance checkpoints are persisted with boards/history, and restored on rejoin. Direct host picks also record accepted progress so an older periodic snapshot cannot undo them. A confirmed host turn is assigned directly, avoiding an extra turn increment merely because a missed history entry was reconciled.

Locations:
- `app/src/main/java/com/bingo/multiplayer/domain/network/MultiplayerSnapshotReconciler.kt`
- `RootNavGraph.kt`: shared broadcast wrapper, direct host progress, restore path and guest `GAME_SYNC` branch.
- `OngoingMatchStore.kt`: serialized snapshot checkpoint.

### G2 — P1: old pause controls overriding a later pause

The existing `pauseEpisode` wire field now represents a monotonically increasing host control revision throughout the match. Pause, extension and actual resume advance it; resume does not erase it. Guests expiring their local display do not invent host revisions.

The revision and whether versioned controls have been accepted survive process restoration. Unpaused snapshots and resume commands carry the revision too. Receivers validate a control before changing UI or saved state. An old pause, extension or resume cannot override a later control, even if the old packet's timestamp is larger. Timestamp high-water marks never decrease.

Versioned `PAUSE_EXTEND` uses JSON through the existing codec so the revision and match identity survive the actual MQTT encoding path. The original unversioned PEX decoder/format remains available for legacy packets. Once versioned control is accepted, unversioned packets cannot replace it.

Locations:
- `MultiplayerMatchLifecyclePolicy.kt`: pause/resume/extend, automatic resume and checkpoint restore.
- `RootNavGraph.kt`: control producers, receiver acceptance, persistence and restore.
- `OngoingMatchStore.kt`: pause control revision, versioned flag and timestamp.
- `FastPacketCodec.kt`: versioned extension encoding.

### G3 — P2: delayed samples adding pause time

A sample carrying the same explicit control revision can only preserve or shorten the accepted pause expiry. A newer sample timestamp alone cannot extend it. Only a newer host control revision can recover an extension or reopen an expired local display. Saved deadlines use the policy's remaining milliseconds, avoiding repeated rounding when saving passive samples.

Legacy timestamp-based extension inference is isolated to matches that have not accepted versioned control. It is not used for current versioned host commands.

## Follow-up review — next batch requires approval

These findings are in separate incoming message paths. Fixes below are proposed; no further implementation was made for them in this batch.

### R1 — P1: an expired direct pick mutates the board before rejection

Location: `RootNavGraph.kt`, `PICK_NUMBER` history merge (around line 2503) and the expected-picker check (around line 2559).

Example: Stuart picked 7 in turn 1, but the packet arrives after that turn expired and turn 2 belongs to Kevin. Its history is merged and 7 is marked before the code notices Stuart is no longer the expected picker and returns. The rejection does not undo the earlier mutation. On the host, a subsequent snapshot can therefore publish the invalid selection as accepted state.

Source-flow reproduction using the production codec, board engine and ID comparison:

```text
LATE_DIRECT_PICK rejected=true turn=2 history=[7] sevenMarked=true
```

Proposed fix: validate the direct packet and every new history entry against the current accepted turn/picker before any board/history mutation. Reuse the actual production move validator/reducer, preserve legitimate catch-up behavior, and publish current host state when rejecting an invalid pending move. Tests must execute that production handler/reducer for direct MQTT picks, rather than only the existing `GAME_SYNC` recovery function. Online 1v1's normal V2 pick path is separate; this finding concerns the legacy 3+ / Nearby handler.

### R2 — P1: a timeout can name the next player as the missed player and process twice

Locations: `RootNavGraph.kt`, eliminated-player skip producer (around line 5013) and `TURN_TIMEOUT` receiver (around line 2676).

The instant-skip producer changes `currentTurnPlayerId` and then uses that new value as the skipped packet's `playerId`. The receiver can mark that next player disconnected. It also accepts an equal-numbered timeout when its `playerId` matches the current player, so a duplicate of this packet advances the turn again.

Example: an eliminated player's turn is skipped into B's turn 4. The packet incorrectly names B as skipped. Its first delivery produces turn 4/B; a repeated delivery produces turn 5/B and resets the timer again.

Source-flow reproduction after a real codec round trip:

```text
TIMEOUT_DELIVERY delivery=1 advance=true turn=4 current=B
TIMEOUT_DELIVERY delivery=2 advance=true turn=5 current=B
```

Proposed fix: capture the skipped player before changing the current player. Distinguish controller identity, closed turn and resulting turn. Apply each authoritative timeout at most once; reject duplicates/obsolete transitions before changing turn, timer or disconnection counters. Add production-path tests for elimination skips, duplicate QoS delivery and repeated turns after other players are eliminated. Preserve the intended zero-time skip for eliminated players.

### R3 — P1: a delayed result from an earlier match can finish a rematch

Location: `RootNavGraph.kt`, `BINGO_CLAIMED` / `GAME_OVER` branch (around line 3367). The adjacent legacy `SURRENDER` path also lacks active-match identity validation.

Example: a previous match used seed 41. The same room starts a new match with seed 42. A delayed win message from Kevin for seed 41 enters the current result handler because it checks game mode and sender but not the active match seed. It can mark a number, declare a winner and clear the new match's recovery record.

Source-flow reproduction:

```text
STALE_MATCH_END packetSeed=41 currentSeed=42 declaresWinner=true
```

Proposed fix: validate match identity, participant/authority and result transition before any result or board mutation. Include match identity on all corresponding outgoing win/surrender controls, preserve legitimate explicit surrender/Bingo results, and extend the online 1v1 legacy filter to cover `GAME_OVER`. Tests should deliver a real old result/surrender after a rematch and verify that boards, result and saved match remain unchanged.
