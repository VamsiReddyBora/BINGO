## N1 fixed — explicit surrender updates the whole turn/roster transition

Locations:

- `domain/network/MultiplayerGameplayReducer.kt`: `surrender`, `pick`, `timeout`, context rotation.
- `domain/engine/MultiplayerMatchLifecyclePolicy.kt`: permanent departure roster, turn-tagged inactivity actions and `isCurrentTurnAction`.
- `domain/network/MultiplayerSnapshotReconciler.kt`: departure roster in accepted host checkpoints.
- `presentation/navigation/RootNavGraph.kt`: rotation, application, persistence, host snapshots and restoration.

An explicit surrender records a permanent receipt, independent of missed turns. If that player owns the open turn, the reducer advances exactly once to an eligible player and assigns the normal 30,000 ms. Surrender during someone else's turn preserves their remaining time. Replays leave the state untouched. Picks and future rotations exclude surrendered players.

The screen applies that state to the lifecycle policy and resets the old decision UI. During pause/HOLD, the new turn is frozen with its own remaining time and match/turn identity. The host saves the resulting turn and roster before publishing its accepted snapshot. Peers receive permanent departures through snapshots, and process restoration restores the same roster into the policy. A heartbeat or rejoin cannot undo an explicit surrender.

Inactivity actions now include the turn number. Before showing a choice or applying a skip, the callback checks both player and turn against the accepted screen state. A queued decision for A/turn 2 cannot affect B/turn 3, or A's later turn. Snapshot validation also rejects a nonterminal state assigning the current turn to a known surrendered player. Existing explicit-surrender result behavior is retained.

## N2 fixed — delayed lifecycle data cannot prove present connectivity

Locations:

- New `domain/network/MultiplayerLifecyclePacketGate.kt`, called before the Root callback's lifecycle effects.
- `RoomMessagePacket`, room-session identity and transport hints in `OnlineRoomSyncManager.kt`.
- Scoped outgoing preparation in `MultiplayerGameplayReducer.kt`; compact presence encoding in `FastPacketCodec.kt`.
- Root presence exchange and existing watchdog integration.

Current-match controls require the active seed/match identity, a known participant and the correct room. Host controls require the original host UID. Explicit departures retain the match in which they were sent; delayed retries cannot be relabelled as a later match. Departure sequence fences reject duplicates and controls older than a verified reply; responses from a newer app instance retire the older instance for the current local session.

Global packet receipt no longer calls `onHostHeartbeat`/`onPeerHeartbeat`. Group presence uses small, avatar-free MQTT request/reply messages every 2.5 seconds. A reply must echo an outstanding nonce, target the requesting player and match its room, match and current local connection generation. Nonces expire after 5 seconds using a monotonic clock; each peer can answer each nonce once. Each participant probes the other match participants, so healthy non-host peers stay visible to each other as well. Only the original host's reply can prove host presence. No phone-clock comparison is needed. Only a valid reply refreshes the existing lifecycle policy. A delayed `GAME_SYNC` or pause packet remains state data and cannot release HOLD.

Probes are non-retained QoS 0, skip disconnected publishing and do not gate picks. Replies are sent only while the app is in the foreground and still in the match. The existing 3-second ready countdown follows a valid return proof. Legacy hold/resume advisory packets cannot override the group's locally verified hold UI.

Broker last-will and transport teardown `LEAVE` packets are hints rather than explicit match exits. They do not terminate or advance an active online match. Nearby's existing direct socket-close/EOF departure behavior is preserved separately and has a regression test. A valid, current-match explicit `HOST_LEFT` keeps the existing host-exit policy. Old seeded game departures cannot close a later lobby; unscoped lobby leave/host-exit behavior remains. Lobby expiry/extension packets cannot apply to an active match.

All participants should install this APK: group presence now depends on the matching request/reply implementation.

## N3 fixed — optimistic Bingo is pending until the controller confirms it

Locations:

- New `domain/network/MultiplayerResultAuthority.kt`, used by local/incoming outcome handling.
- `MultiplayerGameplayReducer.result` and Root pick/result/snapshot paths.
- `MultiplayerSnapshotReconciler`: confirmed result proof and direct host-history checkpointing.

An online group guest still receives immediate sound, vibration and board marking for a permitted selection. A locally computed Bingo does not set the final game-over state, record statistics or clear recovery data. Other guests' claims are proposals for the original host; guests request an accepted host snapshot rather than independently finalizing them.

The host keeps the existing winning-player and runner selection. A guest's stale transient connection indicator cannot veto a proven host-confirmed winner. Its terminal snapshot confirms the accepted history and winner. Bingo proof is calculated from that accepted history, excluding the guest's pending marks. A snapshot from before an in-flight turn preserves its pending mark without confirming a result. A snapshot closing/rejecting that turn removes the mark. A valid terminal snapshot also discards speculative future picks. Explicit host-confirmed surrender/forfeit results have a finished-state marker and retain their existing non-Bingo outcome behavior.

The final review also covered this ordering race: a guest's pending winning pick is timed out by the host, the timeout packet is missed, and a later direct host pick arrives first. Previously the callback could copy the guest's entire local history into the accepted checkpoint, permanently promoting the rejected pick. It now checkpoints only the host packet's actual accepted history. A legacy direct pick without complete history advances the closed-turn fence without promoting local pending history. The next full snapshot can remove the rejected mark normally.

Pending history and the accepted checkpoint remain separate in the recovery record, including after process death. Duplicate/older terminal snapshots do not record a result again. Host terminal snapshots are sent even when the host's pick completes another player's board.

### N6 — P1: group final results are lost to recovery when the host process ends before an offline guest catches up

Locations: [RootNavGraph.kt:882](../../app/src/main/java/com/bingo/multiplayer/presentation/navigation/RootNavGraph.kt#L882), `recordFinishedMatch` and terminal group callbacks; [OnlineRoomSyncManager.kt:796](../../app/src/main/java/com/bingo/multiplayer/domain/network/OnlineRoomSyncManager.kt#L796), `broadcastPacket`; [OngoingMatchStore.kt:318](../../app/src/main/java/com/bingo/multiplayer/domain/network/OngoingMatchStore.kt#L318), `clearOngoingMatch`.

Example: Kevin accepts a legitimate group Bingo while Stuart is offline. The group callbacks record the host's own statistics and clear the active match recovery record. The final `GAME_SYNC` is sent through the ordinary, non-retained room publisher. If Kevin's process then closes before Stuart receives a terminal snapshot, the accepted full result exists only in Kevin's former RAM. After restarting, Kevin has no active checkpoint to reopen and no group result tombstone/full terminal snapshot to answer Stuart's recovery request. Stuart can fail to recover the legitimate outcome. The online 1v1 retained-result path is separate.

The ordinary publisher sets QoS but does not set retain; its MQTT connection uses a clean session. The source does not provide durable terminal group retransmission after process death. This is a source/production-store finding, not a live broker packet-loss reproduction.

Production store probe, combined with separately asserted completion/publisher source flow:

```text
GROUP_FINAL_RECOVERY beforeFinish=true checkpointAfterFinish=false durableResult=false
```

This completion/transport pattern also exists in the exact pre-batch backup. The N3 fix prevents guests inventing a result; it does not create an accepted result when all sources of the host's final state have disappeared.

Proposed next fix: persist an immutable, match-scoped full terminal snapshot/result before clearing active recovery or publishing completion. Provide a bounded MQTT recovery route for that accepted final snapshot after host restart/offline delivery, with duplicate-result suppression and account/match validation. Consider a verified retained terminal record on a separate match topic, preserving the original host as controller and avoiding any HTTP move request. Test guest-offline completion, host process death immediately before/after publish, restart, lost/duplicate final packets and rematch isolation.

### N4 — P2: a valid temporary return-to-lobby can leave the watchdog observing the previous turn

Location: [RootNavGraph.kt:3408](../../app/src/main/java/com/bingo/multiplayer/presentation/navigation/RootNavGraph.kt#L3408), `PLAYER_DISCONNECTED`, specifically the continuation advancing `currentTurnPlayerId` and `turnNumber` without applying the lifecycle turn update.

Example: A returns to the lobby during A/turn 2 in a 3-player match. The host's valid temporary-departure callback advances the screen to B/turn 3. The policy still observes A/turn 2. The new turn fence correctly prevents stale A decisions from skipping B, but the watchdog never starts B's inactivity choice. If B also becomes unavailable, the expected watchdog choice is missing; the ordinary turn countdown remains a separate path.

Production policy plus explicit source-flow probe:

```text
CURRENT_TEMPORARY_DEPARTURE screen=3/B policy=2/A staleActionIgnored=true watchesNextPlayer=false nextPlayerChoice=false
```

Proposed next fix: preserve the existing temporary-departure policy, but route its accepted turn change through the same complete screen/policy/frozen-time/persistence update. Test A leaving the active turn, B then becoming silent, pause and restoration. Temporary lobby departure must remain distinct from permanent surrender.

### N5 — P2: delayed group/Nearby chat can enter a later match

Locations: Root's outgoing `onSendChatMessage` and `broadcastSystemChatMessage`, and the incoming [CHAT_MESSAGE branch at RootNavGraph.kt:2724](../../app/src/main/java/com/bingo/multiplayer/presentation/navigation/RootNavGraph.kt#L2724).

Example: Stuart sends a chat/status message near the end of seed 41. It is delayed while the same room starts seed 42. Group/Nearby chat currently has no required match identity, and the receiver appends/saves it without a match check. The old text can appear in the new match, including an outdated system status message. This does not alter the board or accepted turn sequence. Online 1v1 chat uses the separate V2 path.

Production packet-gate probe plus callback source-flow inspection:

```text
OLD_CHAT packetSeed=41 activeSeed=42 passesGate=true text=Old match message
```

Proposed next fix: stamp the original match identity on group/Nearby chat and system messages before retries; validate it and the participant before appending/persisting. Preserve current chat styling, typing and history behavior. Test delayed messages across rematch, rejoin/restart and duplicate delivery.
