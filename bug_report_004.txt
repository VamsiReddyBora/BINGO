1. EXECUTIVE SUMMARY & SIMULATION OVERVIEW
--------------------------------------------------------------------------------
A dedicated simulation and deep-dive architectural audit was performed focusing
strictly on ONLINE MULTIPLAYER MATCH PLAY in the Android native application.

To test real-world cellular and Wi-Fi conditions, a high-fidelity 10-scenario
multiplayer simulation suite was authored and executed:
`OnlineMatchComprehensiveSimulationTest.kt`. The simulation models 2, 3, 4, 6,
and 8 players across all operational states:
  • Normal turn progression and circular turn rotation.
  • Simultaneous BINGO completions and tie-breakers ("Turn Pick", "Line Count",
    "Turn Priority").
  • Strict Winner, Runner, Loser, and Offline status distribution (zero draw stamps).
  • Turn timeouts with clean turn passing (no auto-picked numbers).
  • Real-world mobile network packet drops (QoS 0 loss simulation).
  • Mid-game disconnections, turn skipping, and offline stamping.
  • Reconnection during ongoing matches via REJOIN_GAME and GAME_SYNC.
  • Post-game flood attacks and rematch (PLAY_AGAIN) cycles.

Full Test Suite Verification:
  • 254 unit and simulation tests executed across 24 test classes.
  • 100% PASS RATE (`./gradlew testDebugUnitTest --rerun-tasks` in 1m 1s).

The core engine and deterministic board generator are highly resilient; however,
4 latent edge cases and synchronization vulnerabilities were discovered under
packet loss, concurrency, and app lifecycle transitions.

DEFECT ID: BUG-013
SEVERITY : MEDIUM
MODULE   : Network Reconciliation & Bottom Bar UI
FILES    : RootNavGraph.kt (lines 1584-1618), GameScreen.kt (lines 1356-1359)
--------------------------------------------------------------------------------
DESCRIPTION:
When a client drops an intermediate PICK_NUMBER packet over lossy networks, then
takes their own turn before catching up, the subsequent reconciliation loop appends
the missed numbers at the end of `pickedNumbersHistory` rather than maintaining
strict chronological order.

ROOT CAUSE:
In RootNavGraph.kt:
```kotlin
// 1. Reconcile any missing numbers from packet's history
packet.pickedHistory.forEachIndexed { idx, num ->
    if (num > 0 && num !in pickedNumbersHistory) {
        val origPickerId = packet.pickedByHistory.getOrNull(idx)?.takeIf { it.isNotBlank() } ?: packet.playerId
        val historicalTurnNumber = idx + 1
        pickedNumbersHistory.add(num)
        pickedByPlayerHistory.add(origPickerId)
        ...
```
Scenario Observed in 8-Player Simulation:
  1. Player 3 drops the in-flight packet for Turn 6 (number 23).
  2. On Turn 7, Player 3's turn begins. Player 3 picks number 17.
     Player 3's local `pickedNumbersHistory` contains: [..., 17].
  3. On Turn 8, Player 4 picks number 8 and broadcasts `pickedHistory`:
     [..., 23, 17, 8].
  4. Player 3 reconciles: 23 is missing from local history, so
     `pickedNumbersHistory.add(23)` appends 23 at the end.
  5. Player 3's resulting history order is: [..., 17, 23, 8], whereas all other
     nodes have: [..., 23, 17, 8].

USER-FACING IMPACT:
In GameScreen.kt line 1356, `RecentPicksQueuePill` reads the last 3 elements of
`pickedNumbersHistory` to render the 3-number FIFO sliding queue pill in the bottom
bar. Because 23 was appended after 17, the visual queue pill displays recent picks
out of chronological order on the recovered client.

REMEDIATION:
When reconciling from an authoritative packet whose `pickedHistory` is strictly
larger and supersedes local history, synchronize `pickedNumbersHistory` to preserve
the authoritative chronological sequence:
```kotlin
if (packet.pickedHistory.size > pickedNumbersHistory.size && 
    packet.pickedHistory.containsAll(pickedNumbersHistory)) {
    pickedNumbersHistory.clear()
    pickedNumbersHistory.addAll(packet.pickedHistory)
    pickedByPlayerHistory.clear()
    pickedByPlayerHistory.addAll(packet.pickedByHistory)
}
```

DEFECT ID: BUG-014
SEVERITY : HIGH
MODULE   : Match Outcome Evaluation & App Lifecycle
FILE     : RootNavGraph.kt (lines 810-820)
--------------------------------------------------------------------------------
DESCRIPTION:
A 10-second heartbeat expiration check inside `evaluateMatchOutcome()` triggers
false player disconnections when a local user backgrounds and resumes the application,
temporarily preventing legitimate winner announcements.

ROOT CAUSE:
In RootNavGraph.kt lines 810-820:
```kotlin
val now = System.currentTimeMillis()
fun isPlayerActive(playerId: String): Boolean {
    if (playerId.isBlank()) return false
    if (isPlayerMe(playerId)) return !isPlayerDisconnected(myUid)
    if (isPlayerDisconnected(playerId)) return false
    val lastHb = if (isUsingP2p) lanP2pSync.getLastDirectHeartbeat(playerId) 
                 else onlineRoomSync.getLastDirectHeartbeat(playerId)
    if (lastHb > 0L && (now - lastHb) >= 10_000L) {
        markPlayerDisconnected(playerId)
        return false
    }
    return true
}
```
Failure Scenario:
  1. The local player backgrounds the app for 12 seconds (e.g., answering a call,
     viewing a notification, or switching apps).
  2. During this period, the backgrounded app paused its incoming packet processor.
  3. When the player resumes, `lastDirectHeartbeat` timestamps stored in local memory
     for active peers are now older than 10,000 ms.
  4. If a winning `PICK_NUMBER` or `GAME_SYNC` packet arrives immediately upon resume,
     `evaluateMatchOutcome()` executes before the next PING cycle updates timestamps.
  5. The check `(now - lastHb) >= 10_000L` evaluates to `true` for all peers, calling
     `markPlayerDisconnected(playerId)` on healthy, active opponents!
  6. `activeCompletedPlayers` becomes empty, suppressing the win declaration.
     The game fails to end on the resuming client until subsequent heartbeats arrive.

REMEDIATION:
Guard the heartbeat staleness check using the foreground resume grace period
already tracked in RootNavGraph:
```kotlin
val isWithinResumeGracePeriod = (now - lastForegroundResumeTimestamp) < 12_000L
if (!isWithinResumeGracePeriod && lastHb > 0L && (now - lastHb) >= 15_000L) {
    markPlayerDisconnected(playerId)
    return false
}
```

DEFECT ID: BUG-015
SEVERITY : MEDIUM
MODULE   : Turn Timer Concurrency & Packet Filtering
FILES    : RootNavGraph.kt (lines 1620-1627, lines 1686-1695)
--------------------------------------------------------------------------------
DESCRIPTION:
A millisecond race condition between a user tapping a cell at 00:00 and the host
firing `TURN_TIMEOUT` causes a 1-turn number desync across peers.

ROOT CAUSE:
In RootNavGraph.kt lines 1621-1627:
```kotlin
val isExpectedPicker = LobbyLifecycleEngine.isPlayerIdMatch(packet.playerId, currentTurnPlayerId) ||
        (packet.isHost && packet.number <= 0) || currentTurnPlayerId.isBlank()
if (!isExpectedPicker && (packet.turnNumber < turnNumber)) {
    // Discard stale out-of-turn packets from previous turns
    return
}
```
And lines 1686-1688:
```kotlin
if (packet.turnNumber > turnNumber || anyNewPick) {
    turnNumber = maxOf(packet.turnNumber, turnNumber + (if (anyNewPick && packet.turnNumber <= turnNumber) 1 else 0))
```

Race Mechanism:
  1. Player 1's turn timer reaches 00:00.
  2. At that exact millisecond, Player 1 taps number 14 (`PICK_NUMBER` sent with
     `turnNumber = 2`). Simultaneously, the Host detects the timeout and broadcasts
     `TURN_TIMEOUT` (`turnNumber = 2`, `number = -1`).
  3. A third peer receives `TURN_TIMEOUT` first:
     • Peer advances local `turnNumber` to 2 and sets `currentTurnPlayerId = Player 2`.
  4. Milliseconds later, `PICK_NUMBER` arrives from Player 1:
     • `isExpectedPicker` is `false` (currentTurnPlayerId is already Player 2).
     • Line 1624 checks: `if (!isExpectedPicker && (packet.turnNumber < turnNumber)) return`.
     • Because `packet.turnNumber == turnNumber` (2 < 2 is false), the packet is NOT discarded!
     • The peer reconciles number 14, marks it on the boards, and line 1687 executes:
       `turnNumber = maxOf(2, 2 + 1) = 3`.
  5. The peer's `turnNumber` increments to 3, while nodes that received `PICK_NUMBER`
     first remain on `turnNumber = 2`.

REMEDIATION:
Enforce that non-host out-of-turn packets are strictly discarded if the packet's
picker does not match the active turn player and is not strictly from a newer turn:
```kotlin
if (!isExpectedPicker && packet.turnNumber <= turnNumber && packet.number > 0) {
    // Discard concurrent move that arrived after turn already rotated
    return
}
```

DEFECT ID: BUG-016
SEVERITY : MEDIUM
MODULE   : Reconnection & Game State Synchronization
FILE     : RootNavGraph.kt (lines 1848-1860)
--------------------------------------------------------------------------------
DESCRIPTION:
When a rejoining player broadcasts `REJOIN_GAME` after a match has ended, the
responding active peer broadcasts `GAME_SYNC` without setting `winnerPlayerId`,
`winReason`, or `runnerPlayerIds`, forcing the rejoining client to reconstruct
the win state via heuristic re-evaluation.

ROOT CAUSE:
In RootNavGraph.kt lines 1848-1860:
```kotlin
broadcastPacket(
    RoomMessagePacket(
        type = "GAME_SYNC",
        turnNumber = turnNumber,
        pickedHistory = pickedNumbersHistory.toList(),
        pickedByHistory = pickedByPlayerHistory.toList(),
        currentTurnPlayerId = currentTurnPlayerId,
        boardHash = engine.computeBoardHash(playerBoard),
        seed = currentMatchSeed,
        playerId = myUid
        // MISSING: winnerPlayerId, winReason, runnerPlayerIds
    )
)
```
Failure Scenario:
  1. A match concludes on a passive tie-breaker (e.g. Player 1 picked, but Player 2
     and Player 4 tied on lines, and Player 2 won via "Turn Priority").
  2. Disconnected Player 3 rejoins and sends `REJOIN_GAME`.
  3. Responding host sends `GAME_SYNC` with empty `winnerPlayerId`.
  4. Player 3 receives `GAME_SYNC` and executes `evaluateMatchOutcome(lastPicker)`.
  5. If Player 3 lacks full participant context or if heartbeat timestamps are
     momentarily cold, Player 3 may fail to declare Player 2 as winner, resulting
     in an unfinalized game screen.

REMEDIATION:
Explicitly serialize the authoritative game-over state into `GAME_SYNC`:
```kotlin
broadcastPacket(
    RoomMessagePacket(
        type = "GAME_SYNC",
        turnNumber = turnNumber,
        pickedHistory = pickedNumbersHistory.toList(),
        pickedByHistory = pickedByPlayerHistory.toList(),
        currentTurnPlayerId = currentTurnPlayerId,
        boardHash = engine.computeBoardHash(playerBoard),
        seed = currentMatchSeed,
        playerId = myUid,
        winnerPlayerId = if (isGameOver) winnerPlayerId else "",
        winReason = if (isGameOver) winReason else "",
        runnerPlayerIds = if (isGameOver) runnerPlayerIds else emptyList()
    )
)
```
